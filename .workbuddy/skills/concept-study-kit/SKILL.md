# 概念学习资料生成 Skill

## 1. 适用场景

**使用本 Skill，当：**

- 用户要"学习 / 搞懂 / 梳理"一个概念（技术概念、方法论、理论模型、产品概念均可）。
- 需要产出一份**可反复复习**的资料，而不是一次性回答（目标物是文件，不是对话）。
- 要求资料里有"机制 + 场景 + 边界 + 来源"四件套，尤其是作业、分享、团队内训场景。
- 需要连续学习多个相关概念，且希望它们**格式统一、可横向对比**。

**不使用本 Skill，当：**

- 用户只想要一句话定义（直接回答即可，不必生成文件）。
- 概念属于**没有公开一手来源**的内部业务术语（此时应转为访谈式提问，不要编造引用）。
- 用户要的是代码、报告、PPT 等其他产物（换用对应 Skill）。

## 2. 输入信息

调用前尽量收集；缺失项按默认值执行，并在资料顶部标注"假设"。

| 输入项 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `concept` | 是 | — | 要学习的概念名，如 `Agent`、`大模型的上下文` |
| `audience` | 否 | "有基本编程经验、AI 领域新手" | 决定解释起点与术语密度 |
| `depth` | 否 | `standard` | `intro` / `standard` / `deep` |
| `output_format` | 否 | `html` | `html` 或 `markdown` |
| `output_path` | 否 | `learning-materials/<concept-slug>.html` | 输出文件路径 |
| `language` | 否 | `zh-CN` | 资料正文语言 |
| `focus` | 否 | 无 | 用户特别关心的问题，如"它和 RAG 有什么区别" |

## 3. 生成步骤

严格按序执行，**不要跳过检索与自检**。

**Step 1 · 定位（Planning）**
明确概念的边界：它是什么、不是什么、属于哪个上层范畴。用一句话写出"这个概念试图解决的问题"。

**Step 2 · 检索（Research）**
至少找出 **3 条一手来源**，优先级：官方技术文档 / 官方工程博客 > 学术论文 > 标准规范 > 权威百科 > 高质量二手解读。
逐条**实际访问验证**（HTTP 200 或能取到正文），死链一律剔除。

**Step 3 · 提炼（Synthesis）**
读来源后**用自己的话**重写。禁止整段复制原文；引用原文必须用引号 + 标注出处，且单条引用不超过 3 句。

**Step 4 · 组织（Structure）**
按 §4 输出结构逐节填充。每节都有硬性要求，见 §4 的"写作要求"列。

**Step 5 · 辨析（Contrast）**
至少列出 3 个易混淆点，每个都写成"误解 → 正解 → 怎么判断"的三段式。

**Step 6 · 自测（Quiz）**
出 5 道题：3 道理解题 + 1 道应用题 + 1 道辨析题。**答案必须折叠或放在文末**，且每题标注对应第几节。

**Step 7 · 自检（Self-check）**
逐条跑 §6 检查清单，任一项不通过就回到对应步骤修改，不允许带着问题交付。

**Step 8 · 交付（Deliver）**
写入 `output_path`，并向用户报告：生成了什么、用了哪些来源、哪些地方做了假设。

## 4. 输出结构

产出文件必须包含以下 8 个部分，顺序固定：

| # | 章节 | 写作要求 |
| --- | --- | --- |
| 1 | 学习目标 | 3–5 条，用"学完你能……"句式，可验证 |
| 2 | 核心问题 | 3–5 个，是资料的导航问题，文中必须逐一回答 |
| 3 | 我的理解（个人解释） | **必须用自己的类比或话术**，不得照搬来源；标注这是个人理解，不是权威定义 |
| 4 | 核心机制 / 组成 | 拆解为 3–6 个部分；配一张文字结构图或表格；说明各部分如何协作 |
| 5 | 应用场景 | **一个具体场景**（有角色、有输入、有步骤、有输出），不要泛泛而谈 |
| 6 | 易混淆问题与使用边界 | ≥3 条，每条用"误解 → 正解 → 判断方法"三段式 |
| 7 | 自测题 | 5 题（3 理解 + 1 应用 + 1 辨析），答案附在文末 |
| 8 | 资料来源 | ≥3 条，每条含：标题、机构/作者、URL、一句话说明它支撑了文中哪部分 |

HTML 输出需额外具备：语义化标签、内嵌 CSS（不依赖 CDN）、目录锚点、来源链接 `target="_blank" rel="noopener"`、页脚标注生成日期与"人工已核查"。

## 5. 资料来源要求（硬约束）

1. **可核查**：必须是他人点击即可访问的公开 URL；生成前逐条验证可达性，验证失败的换掉。
2. **一手优先**：官方技术文档、官方工程博客、论文原文、标准规范优先于二手解读。
3. **禁止伪造**：不确定的链接宁可不写。宁可只写 3 条真实来源，也不凑 8 条似是而非的。
4. **禁止整段照搬**：正文必须是转述；直接引用控制在 3 句内并加引号和出处。
5. **标注时间**：来源旁标注访问日期；涉及数值（如上下文窗口大小）的，注明"以官方文档为准，可能变动"。
6. **区分事实与观点**：来源的客观事实与个人解读/推断要分开写，推断处显式标注"（我的判断）"。

## 6. 自检要求（Checklist）

交付前逐项确认，在文件页脚输出通过情况：

- [ ] 8 个章节齐全，顺序正确。
- [ ] "我的理解"是**自己的表述**，与任何来源段落非逐字雷同。
- [ ] 核心机制拆到 3–6 个部分，且说明了协作关系。
- [ ] 应用场景具体（有角色 / 输入 / 步骤 / 输出），不是空泛举例。
- [ ] 易混淆问题 ≥3 条，均为三段式。
- [ ] 自测题 5 道，答案在文末，且能在文中找到依据。
- [ ] 来源 ≥3 条，**全部实际验证可达**，且覆盖一手资料。
- [ ] 无任何 API Key、密码、个人隐私信息。
- [ ] 全文无"显然 / 众所周知"这类未加论证的断言。
- [ ] 换了另一个概念也能照此流程跑通（无硬编码绑定）。

## 7. 调用示例

```
用 concept-study-kit 学习「向量数据库」，面向有 Python 基础的新手，
深度 standard，输出 HTML 到 learning-materials/vector-database.html，
重点关注「它和传统数据库的索引有什么本质区别」。
```

```
用 concept-study-kit 分别学习 Agent、大模型的上下文、Skill 三个概念，
输出三份 HTML，并额外写一份 concept-relationship.md 说明三者关系。
```
