Skill（智能体技能）

1. 学习目标

  • 学完你能说清一个 Skill 的物理形态（目录 + SKILL.md + 可选子目录）。
  • 学完你能解释"渐进式披露"的三层机制，以及它和上下文窗口的关系。
  • 学完你能区分 Skill、提示词、工具、MCP 这四样东西。
  • 学完你能按规范写出一个合规的 SKILL.md（命名规则、description 写法、引用层级）。
  • 学完你能判断什么任务不该被写成 Skill。

2. 核心问题

  1. Skill 到底是什么？一段提示词？一个插件？
  2. 为什么只加载"元数据"，就能同时挂载几百个 Skill？
  3. 把说明直接写进系统提示，和写成 Skill，差别在哪？
  4. Skill 和 MCP 是什么关系？
  5. 什么情况下 Skill 会失效？

3. 我的理解（个人解释）

类比：书架上的《岗位作业手册》
  • 第一层（书名 + 简介）：Agent 上班时，脑子里只记着每本手册的书名和一句话简介（name + description，约 100 tokens/个）。所以书架上有几百本也不累。
  • 第二层（取下手册读）：遇到相关任务，才把对应的手册从书架上取下来通读（加载完整 SKILL.md）。
  • 第三层（翻附录）：手册里写着"附录 C 见 references/forms.md"，它只在真要填表时才去翻那一页。

我认为 Skill 最巧妙的一点在于：知识存在硬盘上，不占上下文；只在需要的那一刻，才花 token 把它换进上下文。这和"把所有说明一股脑塞进系统提示"是完全相反的思路。

还有一层我特别看重的意义：Skill 是纯文件，所以可以用 Git 管版本、可以评审、可以分享。这意味着"经验"第一次变成了可版本化、可协作的工程资产，而不是散落在聊天记录里的一次性提示词。

阅读提示 以上为个人类比与判断。三层加载机制与 token 量级的原始表述见第 8 节来源 1 与来源 2。

4. 核心机制与组成

4.1 物理结构

skill-name/
├── SKILL.md        # 必需：YAML 元数据 + 指令正文
├── scripts/        # 可选：可执行脚本（Agent 直接运行，不必读进上下文）
├── references/     # 可选：按需加载的详细文档
└── assets/         # 可选：模板、图片、数据文件

关键点是：Skill 就是一个普通目录。没有编译、没有注册中心、没有特殊运行时——这也是它能被 Git 直接管理的原因。

4.2 SKILL.md 的元数据规范

字段必填规则
name是≤64 字符；仅小写字母、数字、连字符；不以连字符开头或结尾；不含连续连字符；必须与目录名一致
description是≤1024 字符；必须同时写清"做什么"和"什么时候用"；应包含触发关键词
license否许可证名称或指向许可文件
compatibility否≤500 字符；环境要求（依赖、网络等）
metadata否自定义键值对，如 author、version
allowed-tools否预授权工具（实验性，各实现支持不一）

合法示例：concept-study-kit、pdf-processing、data-analysis。非法示例：PDF-Processing（大写）、-pdf（开头连字符）、pdf--processing（连续连字符）。

4.3 渐进式披露：三层加载

L1 · 元数据（约 100 tokens）：所有已安装 Skill 的 name + description 在启动时就进入系统提示，常驻。
L2 · 指令正文（建议 < 5000 tokens，文件 < 500 行）：Agent 判断相关时，才读取完整 SKILL.md。
L3 · 资源（按需）：scripts/、references/、assets/ 中的文件，只在被明确引用或需要执行时才加载。

正因为第三层"按需"，一个 Skill 能打包的知识量几乎不受上下文窗口限制——你可以挂一本 200 页的手册，只要它拆成了按需加载的多个文件。

4.4 脚本即工具

Skill 里可以放可执行脚本。好处是：代码不必进入上下文，Agent 直接调用即可。相比让模型每次重新生成同样的代码，这既省 token，又保证结果稳定一致。

4.5 工程属性

  • 可用 Git 做版本管理与 Code Review
  • 非工程师（产品、运营、领域专家）也能编写和维护
  • 可跨团队、跨项目分享复用

5. 一个具体应用场景

本仓库的 concept-study-kit（就是生成你正在读的这份资料的 Skill）

环节实际发生的事
存放位置.workbuddy/skills/concept-study-kit/SKILL.md（项目级，随仓库走）
触发我说"用 concept-study-kit 学习 XX"——命中 description 中的触发词
加载先读 SKILL.md（约 200 行的 8 步流程 + 输出结构 + 自检清单）
执行按流程：定位 → 检索来源 → 提炼 → 8 段结构 → 辨析 → 出题 → 自检 → 产出 HTML
复用效果同一份流程已产出 Agent、上下文、Skill 三份资料，章节结构完全一致；下次学"向量数据库"无需重写提示词

沉淀的价值在哪：如果没有 Skill，我每次都要重新描述一遍"我要什么样的学习资料"，而且每次格式都会漂移。写成 Skill 之后，我对"什么是一份好的学习资料"的判断被固化成了一个可版本化的文件——它现在是仓库的一部分，可以被评审、被改进、被别人拿去用。

我的判断 这才是 Skill 相对"保存好的提示词"最实质的差别：提示词是一次性的输入，Skill 是可积累的资产。前者用完即弃，后者会越用越好。

6. 易混淆问题与使用边界

① 误解："Skill 就是一段保存好的提示词。"

正解：它是带元数据的文件包。核心差别在按需加载——不相关时几乎不占上下文；而且能打包脚本和参考资料，这是纯文本提示词做不到的。

怎么判断：问一句：执行不相关任务时，它还占 token 吗？Skill 不占，写死在系统提示里的会一直占。

② 误解："Skill 和 MCP 是一回事。"

正解：两者解决不同问题——MCP 解决"够得着"（连接外部系统与数据），Skill 解决"会做"（流程、规范、经验）。它们互补而非替代。

怎么判断：去掉它之后，Agent 是"够不着数据/系统"（缺 MCP），还是"不知道该怎么做"（缺 Skill）？

③ 误解："装上 Skill 就自动生效了。"

正解：是否命中完全取决于 description 写得准不准。写得含糊（例如只写"helps with PDFs"），它就永远不会被加载。

怎么判断：用你真实的说话方式触发一次，看它是否被选中；没被选中就改 description，而不是怪模型。

④ 误解："Skill 越多越好，可以挂几百个。"

正解：元数据常驻上下文，每个约 100 tokens；更麻烦的是 description 语义重叠会导致误触发。

怎么判断：监控误触发率和元数据占用，定期清理重叠的 Skill。

⑤ 使用边界：什么样的任务不该写成 Skill

Skill 适合稳定、可复用、能写清楚的流程。一次性的、高度依赖临场判断、或规则每天都在变的任务，写成 Skill 只会得到一份很快过期的文件。

⑥ 编写规范边界

SKILL.md 建议 < 500 行；引用文件保持一层深度（从 SKILL.md 直接链接，不要套娃）；脚本要自包含、有清晰报错。超长内容应拆到 references/。

7. 自测题

  1. 一个 Skill 目录里，哪个文件是必需的？它的顶部必须包含什么？（对应 §4.1、§4.2）
  2. 为什么挂载几百个 Skill 不会撑爆上下文？（对应 §4.3）
  3. description 字段应该写清哪两件事？写得太含糊会导致什么后果？（对应 §4.2、§6-③）
  4. 应用题：你要把"每周竞品分析"流程写成 Skill。请列出你会放进 SKILL.md 的内容，以及你会拆到 references/ 或 scripts/ 的内容，并说明理由。（对应 §4.1、§4.3、§4.4）
  5. 辨析题：团队反馈" Agent 老是选错 Skill"。请给出两个最可能的原因和对应改法。（对应 §6-③、§6-④）
参考答案（先自己答，再展开）
  1. 必需文件是 SKILL.md。顶部必须包含 YAML frontmatter，其中 name 和 description 为必填字段（name 需与目录名一致）。
  2. 因为采用渐进式披露：启动时只加载每个 Skill 的元数据（name + description，约 100 tokens），正文和相关资源只在被判断为相关时才加载。所以挂载数量与上下文占用不是线性关系。
  3. 必须写清"做什么"和"什么时候用"（应含触发关键词）。写得太含糊会导致 Agent 无法判断相关性，从而永远不加载这个 Skill——等于白写。
  4. SKILL.md 放：流程总览（5–8 步）、每步的输入输出、自检清单、以及指向各资源的链接。references/ 放：各竞品的历史分析模板、指标口径定义、输出样例（内容长且只在特定步骤用到）。scripts/ 放：抓取数据、生成图表、套用模板的固定脚本（代码不该反复生成，直接执行更省更稳）。理由：让常驻正文保持精简，把"按需"的部分下沉，符合渐进式披露。
  5. 原因一：description 之间语义重叠或过于宽泛 → 改法：让每个 description 明确写出各自适用场景与触发词，必要时加"不适用于……"。原因二：Skill 数量过多、描述彼此相似，导致误触发 → 改法：合并或下线重叠的 Skill，减少元数据噪音。补充：也可以用真实说法做一轮触发测试来验证改动是否生效。
