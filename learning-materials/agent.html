Agent（智能体）

不是"更聪明的聊天机器人"，而是把"下一步做什么"的决定权从代码交给了模型的系统。

1. 学习目标

  • 学完你能用一句话说清 Agent 与 Workflow、Chatbot 的差别。
  • 学完你能画出 Agent 的"目标 → 规划 → 行动 → 观察"循环，并说明每一步在做什么。
  • 学完你能判断一个具体任务该不该上 Agent，并说出理由。
  • 学完你能列出 Agent 落地的三类风险与对应的控制手段。

2. 核心问题

  1. Agent 和"接了工具的大模型对话"差别到底在哪？
  2. 一个能跑起来的 Agent，最小由哪几部分组成？
  3. 循环里的"观察"这一步为什么是关键？
  4. 什么情况下不该用 Agent？
  5. 怎么防止 Agent 自作主张搞破坏？

3. 我的理解（个人解释）

类比：一个聪明但没进过你公司的实习生
  • Chatbot：他只能坐在工位上回答你的提问，手边没有任何工具，也碰不到公司系统。
  • Workflow（工作流）：你给他一份 SOP——第 1 步查 A 系统、第 2 步填 B 表、第 3 步发通知。他会严格照做，路线是你用代码写死的。
  • Agent（智能体）：你只告诉他目标"帮我把这笔退款处理掉"。他先查订单，发现已退款；再查支付流水，发现银行退票；再判断要不要重新发起、要不要转人工。路线是他根据每一步的真实反馈临时决定的。

所以 Agent 的本质不是"更聪明"，而是控制权的转移：下一步做什么，由模型的判断决定，而不是由代码里的 if-else 决定。这也是我认为判断"这是不是 Agent"最稳的一条标准——比看它叫不叫 Agent 这个名字可靠得多。

4. 核心机制与组成

4.1 六个组成部分

组成作用说明
大脑：大模型规划、判断、决定调用哪个工具负责"想"，是整个循环的决策中心
手：工具集真正改变外部世界查数据库、调 API、执行代码、操作浏览器。MCP 是让工具接法标准化的协议
眼：观察 / 环境反馈拿到真实结果工具返回值、报错信息——这是 Agent 纠错的唯一依据
循环：编排机制驱动多轮迭代见下方流程图
停止条件防止无限循环最大轮数、预算上限、目标达成即退出
上下文 / 记忆本轮能看到的信息详见本系列另一份资料《大模型的上下文》

4.2 运行循环

拿到目标→ 规划下一步→ 调用工具（行动）→ 观察返回结果→ 再规划……→ 满足停止条件 / 求助人类

注意"观察"这一步：正是工具返回的真实结果让 Agent 能纠正上一轮的错误规划。没有观察，就只是 blind 的多轮生成，不是 Agent。

4.3 关键区分：控制流在谁手里

维度Workflow（工作流）Agent（智能体）
控制流写在代码里，路径预先确定由模型在循环中动态决定
适合任务步骤固定、要求稳定一致步骤数事先说不清、需临场判断
可预测性高较低
成本 / 延迟低高（多轮调用，错误会累积）
调试难度低，故障能定位到某一步高，需要沙箱测试与护栏

我的判断 这张表里真正值得记住的是第一行，其余都是它的推论。业界把很多固定流水线也叫"Agent"，但按控制流归属一问就能分辨。名字不重要，决策权在哪儿才重要。

5. 一个具体应用场景

电商客服：退款排障 Agent

要素内容
角色处理"我申请退款了，为什么还没到账"的工单
输入用户订单号 + 一句自然语言描述
可用工具get_order / get_payment_trace / get_logistics / create_refund_ticket / escalate_to_human
输出工单结论 + 给用户的解释 + 完整动作日志

一次真实执行：

  1. 调 get_order → 订单状态显示"已退款"。
  2. 据此决定再调 get_payment_trace → 发现银行侧退票（这才是没到账的原因）。
  3. 判断处理路径：重新发起退款，或补充说明转人工。
  4. 护栏生效：若退款金额 > 500 元，强制走 escalate_to_human，不允许自行动作。

为什么这里适合用 Agent：要查几个系统、查出什么结果、下一步该查什么，完全取决于银行和物流返回的数据——你事先写不完所有分支。这正是"步骤数无法预判"的典型场景。

配套护栏：退款额度上限、不可逆动作必须人工确认、每一步写日志可回放。

6. 易混淆问题与使用边界

① 误解："Agent 就是能多轮对话的聊天机器人。"

正解：区别在于是否具备工具 + 环境反馈 + 自主决定下一步。只会聊天、碰不到任何外部系统的不是 Agent。

怎么判断：问一句——它能不能改变外部世界的状态（改数据库、发请求、写文件）？不能，就不是。

② 误解："Workflow 和 Agent 只是叫法不同。"

正解：Anthropic 的划分标准是控制流在代码里还是在模型里，这是架构差异，不是措辞差异。

怎么判断：换一个没见过的输入变体，流程还走得通吗？需要改代码才能走通的是 Workflow。

③ 误解："越自主越好，上 Agent 就一定更强。"

正解：Agent 是用延迟和成本换任务表现，而且单步小错会在多轮中累积。很多场景"单次调用 + 检索 + 几个示例"就足够了。

怎么判断：先跑一个最简单的 baseline，用数据证明增加的复杂度值得，再上 Agent。

④ 误解："接的工具越多，Agent 越强。"

正解：工具定义本身要占用上下文，工具描述写得含糊会让模型频繁误用。接口质量决定上限，不是数量。

怎么判断：盯"工具误用率"这个指标，而不是工具数量。

⑤ 使用边界：不可逆 / 对外可见的动作

删库、发邮件、强制推送、对外发布——这类动作必须人工确认或在沙箱中隔离执行。自主性越高，越要提前设好"刹车"。

7. 自测题

  1. 用一句话说明 Agent 与 Workflow 的本质区别。（对应 §4.3）
  2. Agent 循环中有一步叫"观察"，去掉它会发生什么？（对应 §4.2）
  3. 为什么说"工具数量多"不等于"Agent 强"？（对应 §6-④）
  4. 应用题：你的团队要做"每月销售报表自动生成"，步骤固定为取数→清洗→出图→发邮件。该用 Workflow 还是 Agent？说明理由。（对应 §4.3、§6-③）
  5. 辨析题：某产品宣称"我们的 Agent 有 200 个工具"，但实际只是把 200 个 API 按固定顺序串成流水线。它更接近什么？为什么？（对应 §6-②）
参考答案（先自己答，再展开）
  1. 控制流归属不同：Workflow 的控制流写在代码里、路径预先确定；Agent 的控制流由模型在循环中动态决定。
  2. 没有观察，Agent 就拿不到真实反馈，只能凭自己的输出继续生成——错误无法被纠正，多轮迭代失去意义，退化成盲目的连续生成。
  3. 工具定义要占用上下文窗口，工具描述不清会导致误用；真正决定效果的是接口质量（描述是否清晰、参数是否自解释、边界是否写明），而非数量。
  4. 应该用 Workflow。四个步骤固定、输入输出明确、要求稳定一致，没有需要临场判断的分支。上 Agent 只会增加成本、延迟和出错概率，却换不来收益。
  5. 更接近 Workflow。判断依据是控制流在代码里（固定顺序串联），而不是模型根据反馈动态决定；"Agent"在这里是营销标签。可换一个未见过的输入变体验证：若必须改代码才能处理，就是 Workflow。
