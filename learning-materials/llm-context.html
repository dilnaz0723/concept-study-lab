大模型的上下文（Context）

模型每次推理时能看到的全部 token。它不是记忆，而是一份每次请求都要重新提交、且容量有限的输入。

3. 我的理解（个人解释）

类比：一张固定大小的办公桌
  • 上下文 = 桌面上摊开的纸。桌子尺寸固定，这就是上下文窗口上限。
  • 每次请求都要把纸重新摆一遍。模型本身不记得上次对话，会话"看起来连续"，是因为程序每轮都把历史重新发了一遍。
  • 纸越多，每张分到的注意力越少。哪怕桌子够大，摊 500 张纸时模型也不可能对每张都同样上心。
  • 最容易被忽略的是中间那摞。放在开头和结尾的信息最容易被用上，中间的最容易被漏掉。

所以"上下文工程"说白了就是一件家务事：在有限的桌面上，只留下此刻最有用的几张纸——其余的别放、压缩成摘要、或者塞进抽屉（外部文件 / 记忆），等真需要时再拿出来。

4.1 上下文里装了什么

4.2 为什么它是有限的（四层原因）

  1. 硬上限：窗口有 token 上限，输入和输出一起算，超了请求会直接失败。
  2. 注意力预算：基于 Transformer 架构，n 个 token 之间存在 n² 级别的成对关系。上下文越长，这份预算被摊得越薄。
  3. 位置偏差（U 形曲线）：关键信息在开头或结尾时表现最好，在中间时显著下降。
  4. 上下文腐烂（context rot）：窗口内 token 越多，模型准确召回其中信息的能力整体下降。

4.3 五种管理手段

手段怎么做解决什么失效
即时加载（JIT）不预先塞满，需要时让 Agent 用工具去取上下文被无用信息占满
压缩 / 上下文编辑自动清掉过期的工具结果，或把旧对话摘要成一段长对话跑不下去
提示缓存把稳定的前缀（系统提示、工具定义）缓存复用重复发送导致的成本（省钱，不省 token）
记忆工具把要长期保留的信息写到外部文件，跨会话存在会话结束即失忆
工具搜索 / 程序化调用工具多了才加载定义；把一串调用合成一个脚本执行工具定义与中间结果撑爆窗口

我的判断 这五种手段不是五选一，而是治不同的病：JIT 治"塞太多"、压缩治"跑太长"、缓存治"太贵"、记忆治"记不住"、工具搜索治"工具多"。先定位自己在哪个环节出问题，再选手段——上来全堆一遍是浪费。

5. 一个具体应用场景

代码库级重构 Agent：如何不被上下文拖垮

内容处理策略
系统提示 + 工具定义内容稳定 → 使用提示缓存，避免每次重复付费
读文件 / 跑测试的结果几十轮后大量堆积且已过时 → 上下文编辑自动清除
架构决策、踩坑记录必须跨会话保留 → 写入记忆文件，下次开工先读
硬性约束（命名规范、禁止改动目录）放在系统提示最开头，避开中间盲区
具体代码内容不预先全量加载 → 即时加载，用到哪个文件读哪个

不这么做会怎样：任务跑到中途上下文耗尽，请求直接失败；或者勉强跑完，但模型因为注意力被稀释而开始漏掉早期约束、改错文件。

效果参考：Anthropic 公布的内部评测显示，在 agentic search 任务上，"记忆工具 + 上下文编辑"组合相比 baseline 性能提升 39%，单独使用上下文编辑提升 29%；在 100 轮 web search 评测中，上下文编辑让原本会因上下文耗尽而失败的任务得以完成，同时 token 消耗降低 84%。

数据使用提醒 上段数字来自厂商自测的官方发布（来源 4），用于说明量级与趋势，不应当作跨产品可直接对比的基准。具体窗口大小与产品能力请以官方文档为准，会随版本变动。

6. 易混淆问题与使用边界

① 误解："上下文窗口就是模型的记忆。"

正解：上下文是每次请求重新提交的无状态输入，请求结束就没了；跨会话保留必须依赖外部存储（记忆文件、数据库）。

怎么判断：新开一个对话，它还记得上周的结论吗？不记得——那之前只是上下文，不是记忆。

② 误解："窗口越大越好，100 万 token 就能整本塞进去。"

正解：容量 ≠ 有效利用。注意力稀释和位置偏差会让"塞满"反而降低精度。目标是放进最小的高信号 token 集，不是放进最多的内容。

怎么判断：做检索精度测试，别只验证"能不能塞下"。

③ 误解："RAG 和长上下文是同一件事。"

正解：RAG 是"先检索、只把相关的放进来"；长上下文是"容量更大"。两者解决的是同一个问题的不同侧面，可以叠加使用。

怎么判断：看信息是预先全塞进去（长上下文思路）还是按需取回来（RAG 思路）。

④ 误解："压缩 / 摘要是无损的。"

正解：压缩必然丢细节，关键数值、ID、专有名词可能被改写或丢失。

怎么判断：压缩前，把绝对不能丢的事实显式写进记忆文件，不要指望摘要会保留它们。

⑤ 使用边界（安全）：任何进上下文的内容都会被发送给模型服务商

API Key、密码、身份证号、未脱敏的客户数据——一旦进入上下文就已外发。这类内容必须在进入前脱敏或拦截，不能指望"它应该不会记住"。

⑥ 使用边界（数值）：窗口大小会变

不同模型、不同版本的上下文窗口差异很大，且会调整。引用具体数字时务必以官方文档当前版本为准，本资料因此不写死任何具体数值。

7. 自测题

  1. 列举至少 4 类会计入上下文的内容。（对应 §4.1）
  2. 为什么上下文变长后，模型的表现反而可能下降？说出两个原因。（对应 §4.2）
  3. "提示缓存"省的是什么？不省的是什么？（对应 §4.3）
  4. 应用题：你的 Agent 每次跑 30 轮后就报"上下文超限"。请说出两种处理思路，并说明各自解决什么问题。（对应 §4.3）
  5. 辨析题：同事说："我们把整个产品手册塞进系统提示了，模型现在什么都知道。"请用本资料的概念指出这句话的两个问题。（对应 §4.2、§6-②）
参考答案（先自己答，再展开）
  1. 系统提示、对话历史、工具定义、工具返回结果、附件与技能、思考块与输出（任选 4 类即可）。
  2. ① 注意力预算被摊薄：n 个 token 之间的成对关系随长度增长，模型难以同等对待全部内容；② 位置偏差：位于上下文中间的信息最容易被忽略；③ 上下文腐烂：token 越多，准确召回能力整体下降。（答出任意两个）
  3. 提示缓存省的是成本（重复发送相同前缀时按缓存价计费），不省 token——这些 token 依然占用上下文窗口，依然消耗注意力预算。
  4. 思路一：上下文编辑 / 压缩，自动清掉已过期的工具结果，解决"跑太长"；思路二：即时加载，不要把文件全量预先塞进去，用到再取，解决"塞太多"；思路三（加分）：把跨轮次必须保留的结论写入记忆文件，解决"清掉之后又要用到"的矛盾。
  5. 问题一：容量不等于有效利用——手册塞进去了，但模型对其中内容的召回会随总量上升而下降，尤其是"中间"部分（位置偏差）；正确做法是只放入当前任务相关的高信号内容。问题二：成本与注意力——每次请求都要重发整本手册，成本高且稀释注意力；应改为检索式按需取用（RAG / 即时加载），或用提示缓存降低成本。
